术语表

收录原则有三条。第一，词条以中文译本 原站术语表 的 61 条为底，另外补了 46 条书里反复出现、原表没收的词（复制滞后、写偏斜、水位线、栅栏令牌……），因为在评审里漏掉这些词比漏掉「无界」严重得多。第二，每条都给准确定义 + 最常见误用 + 对应课程——在系统设计面试里，把「线性一致」说成「强一致」不是措辞问题，是让对方无法判断你承诺了什么。第三，按主题分组，不按字母序：中文读者查词靠的是「它属于哪一类问题」，不是首字母。

查词的正确姿势：先找这词在哪一组，再读它的 → 指到哪一课。术语表的定义只能让你不再说错，能让你在评审里接得住追问的是那一课。

一 · 数据系统与架构

这一组词都在回答同一个问题：这份数据的权威版本在哪，其他都是谁的副本？

数据密集型data-intensive

数据的管理方式（体量、变更传播、并发与故障下的正确性）是主要挑战的应用。对应的是计算密集型，难点在把庞大计算并行化，拼的是 FLOPS 与互连带宽。

别说成「数据量大的应用」。十 GB 也可能很数据密集，一 PB 的冷归档可能一点不密集。

→ L1 数据系统架构中的权衡

事务型系统OLTP · online transaction processing

由创建数据的后端服务构成、按用户操作做点查询与单条增删改的系统。查询集合由应用代码预先写死，数据表示的是当前状态。

别理解成「小查询」。判据是访问模式（点查 + 当前状态），不是查询大小。

→ L1

分析型系统OLAP · online analytical processing

保存事务型系统的只读副本、服务分析师与数据科学的系统。典型访问是扫描海量记录做聚合，查询由人临时写、还可能由 BI 工具自动生成，数据表示的是事件历史。

别说「OLAP = 数据量大」。真正的差别是「查询能否预先定义」与「表示当前态还是历史」。

→ L1

记录系统system of record · source of truth

持有某类数据权威版本的系统。判据只有一句：这份数据丢了，能不能从别处重新算出来？不能，它就是记录系统。

别按产品类型判断（「数据库就是记录系统，缓存就是衍生数据」）。同一个 Redis 既可能是缓存，也可能是某份配置的权威来源，取决于它在应用里怎么被用。

→ L1

衍生数据derived data

通过可重复流程由其他数据生成、必要时能重新计算的数据集。索引、缓存、物化视图、搜索索引、报表都属此类。技术上冗余，但为了读性能往往不可或缺。

别把「衍生」当成「不重要」。衍生数据错了要能发现、能重建，这本身是一套工程要求（对账、校验和、可重跑）。

→ L1

ETLextract-transform-load

从源库抽取、转成适合分析的形式、再加载进数据仓库或批处理系统。ELT 是把转换推迟到加载之后（利用仓库自身算力），取舍在于「转换逻辑放哪、谁维护」。

别把 ETL 当纯工具问题。它决定了衍生数据的重建成本：重建要跑多久，直接决定故障恢复的 RTO。

→ L1

数据仓库data warehouse

把多个 OLTP 系统的数据汇总整理后供分析使用的独立数据库。它存在的四条理由：数据孤岛、模式不合适、分析开销会外溢到在线服务、网络隔离。

别说「仓库就是把数据复制一份」。复制一份谁都会，难的是跨源对齐口径与时间语义。

→ L1

容错fault-tolerant

出现故障（机器崩溃、链路中断、磁盘坏块）后系统仍能自动恢复并正确工作。关键区分：故障（fault）是部件偏离规格，失效（failure）是系统整体停止提供服务；容错就是阻止前者变成后者。

别说「我们不会出故障」。要说的永远是「我们假设哪几类故障、不假设哪几类」。

→ L2 定义非功能性需求

无共享shared-nothing

每个节点有独立 CPU、内存、磁盘，仅通过普通网络协作的架构。相对的是共享内存与共享磁盘。它的好处是横向扩展与故障隔离；代价是所有协调都要走网络，而网络是异步且不可靠的。

别把「无共享」当成「无需协调」。恰恰相反，无共享把所有协调成本显式暴露出来了。

→ L2

可伸缩性scalability

负载增长时系统仍有合理办法应对的性质。它是一个关系，不是属性：必须先量化负载（每秒请求数、读写比、数据量、峰值与均值倍数），才谈得上「可扩展」。线性扩展、主动伸缩与被动伸缩是三个不同的说法。

别说「这个系统是可扩展的」。要说「在 X 负载下，加一倍节点能带来百分之几的吞吐」。

→ L2

可维护性maintainability

可运维（operability）、简单（simplicity）、可演化（evolvability）三项的合称。书里给它的定位很硬：它是唯一一项你每天都要付利息的维度。

别把可维护性当成「代码风格」。在数据系统里它的具体形态是：加一个字段要动几个服务、换一个存储引擎要重写多少、排一次故障要开几个面板。

→ L2

二 · 数据模型与编码

这一组问的是后果：选了它，我后面被锁死了哪些事？

关系模型relational model

数据表示为无序的行（元组）集合，通过声明的键与连接表达关系。它的优势是连接是一等公民，多对多不需要应用层拼装；代价是模式相对刚性与对象-关系阻抗。

别说「关系模型过时了」。绝大多数 N+1 查询问题的根因是用文档模型存了本该连接的数据，不是关系模型不好。

→ L3 数据模型与查询语言

文档模型document model

数据表示为自包含的文档（通常是 JSON），一棵树存一个实体及其嵌套部分。它擅长一对多（整棵树一次读出、局部性好），不擅长多对多（要应用层 join 或反规范化）。

别说「文档模型不需要模式」。模式只是从写入时移到了读取时（schema-on-read），代价由每个读者承担。

→ L3

图graph

由顶点（vertices，也称 nodes/entities）与边（edges，也称 relationships/arcs）组成的数据结构。适合高度互联、连接深度不可预知的数据（社交关系、路网、欺诈链路）。

别因为「有外键」就说自己在用图模型。判据是查询需要在未知深度上遍历。

→ L3

事件溯源event sourcing

把不可变的事件日志作为权威数据源，当前状态由事件重放派生出来。它把「记录系统」和「衍生数据」的关系显式化了，天然支持审计与时间旅行。

别说「事件溯源 = 存一份变更日志」。变更日志是复制机制，事件溯源是数据模型的选择：事件本身是业务事实，不是数据库内部记录。

→ L3 与 L13 流式系统的哲学

物化materialize

把计算结果提前算好写下来，而不是每次按需即时计算。物化视图、缓存、索引都是物化的不同形态。物化就是制造衍生数据。

别以为物化只是性能优化。一旦物化，你就多了一份会与源数据不一致的副本，也就多了一份要监控、要重建的责任。

→ L3

声明式declarative

描述「想要什么性质」，而不是「如何一步步实现」。SQL 是声明式，因为查询优化器可以自由改执行计划；命令式代码把执行顺序写死了，优化空间被作者提前花掉。

别说「声明式一定更快」。声明式给的是优化空间，优化器不行时它反而更慢，这也是为什么还要看执行计划。

→ L3

规范化normalized

数据结构中尽量避免冗余与重复，使一处变化只改一处。代价是读要连接多个表。

→ L3

反规范化denormalize

在已规范化的数据里引入冗余（缓存、索引、冗余列）换取更快的读。反规范化的值本质上是预计算结果，与物化视图同类。

别把反规范化当成「为了性能可以先乱来」。每一处反规范化都要说清：谁负责同步、不一致时以谁为准。

→ L3

连接join

把有引用关系的记录拼在一起。在关系模型里是数据库的活，在文档/分布式模型里往往变成客户端的活，甚至变成一条跨分片的网络往返。

别说「join 慢所以要反规范化」。先分清是缺索引、跨分片、还是数据布局问题，三者代价差一到两个数量级。

→ L3 与 L7 分片

数据框dataframe

第二版新增的模型：把数据看成带列名的二维表，在其上做变换组合（filter / join / groupby / pivot）。它成了数据分析的事实标准，因为抽象层级正好落在「一张表的变换」——比 SQL 更可组合，比手写循环更可利用优化器（如 Apache Spark 的 Catalyst）。

别说「数据框就是内存里的表」。它的价值在于变换是可组合的表达式，而不是某个具体实现。

→ L3

模式schema

对数据结构的描述（字段、类型、约束）。检查时机可以在写入时（schema-on-write）或读取时（schema-on-read）；模式也可随时间演进。

别说「无模式」。只有「什么时候检查」的区别，没有「有没有」的区别。

→ L5 编码与演化

前向兼容forward compatibility

旧代码能读新代码写的数据。它比后向兼容难，因为旧代码无法预料新字段，只能靠「忽略不认识的字段 / 保留未知字段」这类编码设计。

别说「我们前后兼容都做到了」而不说机制。机制只有几类：可选字段 + 默认值、保留字段号、显式版本标记、schema registry。

→ L5

后向兼容backward compatibility

新代码能读旧代码写的数据。这是最容易做也最容易忘的一条：只删不加、只加可选字段，后向兼容几乎免费。

→ L5

三 · 存储与检索

这一组的判据是一个数：这一次逻辑写入，在磁盘上变成了几次物理写入？答不出这个数，就不知道自己的写吞吐上限在哪。

日志结构合并树LSM-tree · log-structured merge tree

写入只追加、不原地更新：新数据先进内存表（memtable），刷盘成不可变的 SSTable，后台再把多个 SSTable 归并压实。读要按「内存表 → 新 SSTable → 旧 SSTable」逐层查找，所以写入便宜、读取代价高。

别说「LSM 比 B 树快」。它在写密集负载下快，在读放大与空间放大上要还债，尤其范围查询要合并多层。

→ L4 存储与检索

SSTablesorted string table

按键有序、不可变的磁盘文件，带稀疏索引与块级校验和。不可变是关键：文件一旦写成不再修改，所以并发读不需要加锁，压实只需整文件重写。

→ L4

B 树B-tree

把数据按固定大小的页（通常 4KB）组织成平衡树，页内原地更新。它的写放大来自「改一个字节也要写一整页」，且必须配预写日志才能保证崩溃安全，所以一次逻辑写至少变成两笔物理写。

别说「B 树已过时」。它的读放大稳定、范围扫描连续，所以在读多写少与事务型负载里仍是默认选择。

→ L4

写放大write amplification

一次应用层写入导致的物理写入字节数。B 树通常 ≥2（日志 + 页）；LSM 在稳态下由压实倍数决定，层数越多倍数越高（典型 10–30）。它是把「写吞吐」换算成「磁盘带宽」的那个系数，闪存寿命也直接吃这个数。

别只谈 IOPS 不谈写放大。同样的 IOPS 预算，写放大 20 的系统实际能承载的写入只有 5%。

→ L4

压实compaction

后台把多个 SSTable 归并重写、丢弃被覆盖或已删除的版本。它带来两个副作用：磁盘带宽被后台任务吃掉（前台 p99 抖动的主因），以及压实跟不上写入时读放大持续恶化。

别说「后台任务不影响前台」。压实与前台写共享同一块盘，限流做不好就是尾延迟灾难。

→ L4

堆文件heap file

记录无序存放的数据文件，索引只存指向记录的指针。好处是一条记录只存一份、多个索引可共存；代价是索引命中后还要按指针再读一次（随机 I/O）。

→ L4

聚簇索引clustered index

索引里直接存行数据（或按索引键的物理顺序存行），所以主键查找一次 I/O 到位，代价是一条记录只能有一种物理顺序，二级索引要回表。

别说「聚簇索引一定更快」。它把顺序押在主键上：随机主键（UUID）会让插入点分散到全表，反而制造写热点。

→ L4

二级索引secondary index

按非主键属性建立的索引。它天然是「一份必须与主数据保持一致的衍生数据」，所以每个二级索引都是一笔要在写入路径上偿付的维护成本。

→ L4 与 L7 分片

列式存储column-oriented storage

把同一列的值连续存放，而不是按行。三个收益叠加：只读查询涉及的列（I/O 少一个数量级）、同列同类型压缩率高（位图 / 游程 / 字典）、排序后可用最小最大索引跳过整块。

别说「列存适合大数据」。判据是访问模式是否是「少数列 × 海量行」的聚合；点查与整行读写它反而更差。

→ L4

位图编码bitmap encoding

对低基数（不同取值很少）的列，为每个取值存一个比特位图，查询时按位与/或直接得到行号集合。它让「性别 = 女 且 城市 = 北京」这类条件变成几次内存位运算。

别对有高基数的列用位图。取值一多，位图数量爆炸，压缩率与查询速度同时崩掉。

→ L4

数据立方data cube · OLAP cube

按多个维度预先聚合好的物化结果，查询时按维度组合取格子。它是「用空间换时间」的极端形态：格子数是各维度基数之积，维度一多就不可维护。

别说「建个 cube 就好了」。先算格子数：10 个维度各 20 个取值就是一万亿个格子。

→ L4

四 · 复制与分片

这一组绕不开三个事实：这份数据现在有几份、谁说了算、读者看到的是哪一份？

复制replication

把同一份数据保存在多个节点上。它同时服务四个目的：降低延迟（就近读）、提高可用性（故障切换）、提高读吞吐（分摊查询）、以及地理合规。这四个目的经常互相冲突，所以「为什么要复制」必须先说清是哪一个。

→ L6 复制

领导者leader · master · primary

唯一接受写入的副本，写入先经它排序再传播给其他副本。单主的价值不在于性能，而在于把并发写变成了一个全序——没有这个全序，冲突解决就得在每个副本上重做一遍。

→ L6

追随者follower · read replica · secondary

从领导者接收变更日志并应用的副本，通常只服务读。它读到的数据落后领导者多久，就是复制滞后。

→ L6

复制滞后replication lag

从写入在领导者上提交，到该变更在某个追随者上可见之间的时间差。它不是一个可调参数，而是「网络 + 排队 + 应用日志」的合力，负载高峰会放大一个数量级。

别说「最终一致，所以滞后无所谓」。滞后 3 秒意味着用户刚保存的内容刷新后消失——这是可见的产品缺陷，不是理论问题。

→ L6

读己之写read-your-writes consistency

用户读到的数据至少包含他自己刚写的内容。实现套路有三种：读自己的东西走主库、记住写入的时间戳并只读追平到该时间戳的副本、或按会话粘住同一副本。

别说「我们做了最终一致所以没问题」。最终一致不保证这个，用户提交后看不到自己的提交是最常见的投诉来源。

→ L6

单调读monotonic reads

用户不会看到时间倒流：一旦读到某个版本，之后不会再读到更旧的版本。它防的是「刷新一下数据退回三秒前」，多副本负载均衡到不同滞后程度的节点时必然出现。

→ L6

一致前缀读consistent prefix reads

读到的写入序列符合因果顺序：不会出现「答案先到、问题后到」。分片之后特别容易违反：两个有因果关系的写落在不同分片、各自复制，观察者可能先看到后果。

→ L6

多主multi-leader replication

多个节点都接受写入、彼此异步传播。它换来了跨地域写入的低延迟与断网期间的可写，代价是写冲突必须在某处解决：最后写入者胜（丢数据）、版本向量（要人工介入）、或 CRDT（限制数据类型）。

别说「多主就等于高可用」。多主把冲突从「不会发生」变成「每天发生，只是你还没看见」。

→ L6

无主leaderless replication

客户端直接向多个副本写、向多个副本读，靠法定人数保证读到最新值。它没有故障切换这个动作（也就没有切换失败这个故障模式），代价是把协调责任推给了客户端与应用语义。

→ L6 与 L10 一致性与共识

法定人数quorum

读集合与写集合相交的最小规模：w + r > n。这个不等式保证读写至少碰到一个共同副本，从而「读到最近一次写」。但它只保证相交，不保证线性一致——没有额外机制时，仍可能读到旧值。

别说「配了 quorum 就是强一致」。并发写、失败重试、以及「读修复尚未收敛」都会破坏它；法定人数给的是概率性的新鲜度，不是线性一致。

→ L10

读修复read repair

读时发现某个副本落后，顺手把新值写回去。它让「被读到的数据」自动收敛，但冷数据永远得不到修复，所以还需要反熵过程兜底。

→ L6

反熵anti-entropy

后台持续比对副本间的差异并同步。它不依赖读流量，所以能修好冷数据，代价是常态下的额外带宽与比对开销。

→ L6

提示移交hinted handoff

目标副本暂时不可用时，由别的节点代存写入并在恢复后转交。它避免了「一个副本挂掉就拒绝写」，但代存节点的磁盘成了新的故障点。

→ L6

脑裂split brain

两个节点都认为自己是领导者、都接受写入，于是数据分叉。防它的不是「检测得更快」，而是法定人数 + 栅栏令牌：少数派一侧必须主动拒绝服务。

别说「我们有健康检查所以不会脑裂」。健康检查判断的是「我看得见对方吗」，不是「对方还活着吗」，网络分区下这个判断必然出错。

→ L10

分片sharding · partitioning

把大数据集拆成多个分区放到不同节点。它与复制的分工要分清：分片解决「一份数据放不下 / 一个节点扛不住」，复制解决「节点会坏」；两个维度正交，组合起来才是真实的集群。

→ L7 分片

再平衡rebalance

把数据从负载高的节点迁到负载低的节点，或在增删节点后重新分配。判据是「迁移过程中服务是否可用、迁移量是否与数据总量成正比」。好的方案只搬该搬的那部分。

别说「加机器就能扩容」。如果方案是 hash(key) % n，加一台机器几乎要搬全部数据。

→ L7

偏斜skew · hot spot

分区之间负载严重不均，个别分区成为瓶颈。它有两种来源：键本身分布不均（少数大客户），或访问模式不均（同一个键被疯狂读写）。前者靠选键与拆键，后者只能靠缓存或拆写。

别说「哈希就均匀了」。哈希只保证键的数量均匀，不保证每个键的访问量均匀，热点是后者。

→ L7

一致性哈希consistent hashing

把键与节点映射到同一个环上，键归顺时针方向第一个节点。增删节点只影响相邻区段，迁移量与节点数成反比而不是与数据量成正比。

→ L7

按词条分区term-partitioned index · global index

二级索引按被索引的词条本身分区，而不是跟着文档走。这样按词条查询只打一个分区，但一次写入要更新分布在各处的多个索引分区，写变成分布式事务级的问题。

别说「索引跟着数据走就行」。那是按文档分区（local index），读时要 scatter/gather 所有分区，尾延迟由最慢的那个决定。

→ L7

五 · 事务与并发

这一组要求你说出异常的名字：这段代码被并发执行时，数据库承诺不出现哪一种交错？说不出名字，就证明不了自己选的隔离级别够用。

事务transaction

把多个读写打包成一个逻辑单元，要么全部生效、要么全部不生效。它的价值是把「部分失败」这种最难处理的状态从应用代码里删掉——这是工程收益，不是理论洁癖。

别说「事务影响性能所以能不用就不用」。多数情况下真正影响性能的是长事务持有锁，而不是事务这个抽象本身。

→ L8 事务

原子性atomicity

事务内的一组写入要么全部提交、要么全部回滚，不存在中间态。注意它不等于并发隔离：原子性管的是「中途崩溃」，不是「两个事务互相看见半成品」。

别把原子性和隔离性混为一谈。前者是失败语义，后者是并发语义；ACID 里这两个字母经常被一起误用。

→ L8

隔离性isolation

并发事务之间互不干扰的程度。实践中它是一组可选的级别，每个级别对应「允许哪种异常发生」。

别说「我们是 ACID」。ACID 的 I 在实践中几乎从不取最强值，说清级别与代价才算说了。

→ L8

持久性durability

事务提交后，即使断电或崩溃数据也不丢。实现方式从「写入即 fsync」到「先写日志、异步刷盘」不等；后者在崩溃时可能丢最后几百毫秒，这是要写进承诺的取舍。

别说「写进数据库就安全了」。要知道它承诺的是「进程崩溃不丢」还是「磁盘损坏也不丢」，后者需要副本或校验。

→ L8 与 L9 分布式系统的麻烦

读已提交read committed

只允许读到已提交的值，禁止脏读与脏写。这是多数数据库的默认级别。它的漏洞是会「同一事务内两次读到不同值」（不可重复读）与「读到别人刚提交的新行」（幻读）。

→ L8

快照隔离snapshot isolation

每个事务读到自己开始时刻的一致快照，写冲突在提交时检测。它消除了不可重复读与幻读，代价是写偏斜仍然可能发生：两个事务读同一段、写不同行，谁也检测不到冲突。

别说「用了快照隔离就没有并发问题了」。写偏斜是这一级别最著名的漏洞，也是面试里最常被追问的一点。

→ L8

写偏斜write skew

两个并发事务各自读取一组行、基于读到的值写入另一组行，两次写的行不重叠，因此行级写冲突检测看不到冲突，但组合结果违反了一条业务不变式（例如「至少一名医生值班」）。

别说「加唯一索引/加行锁就能防」。它防的是写同一行的冲突；写偏斜的本质是「读集合与写集合交叉」，只有可串行化或显式加锁（SELECT FOR UPDATE）能挡。

→ L8

可串行化serializable

最强隔离级别：并发执行的结果等价于按某个串行顺序执行。三种实现各有代价：两阶段锁（排队与死锁）、可串行化快照隔离 SSI（误判与重试）、单线程串行执行（吞吐天花板）。

→ L8

两阶段锁two-phase locking · 2PL

读加共享锁、写加排他锁，持锁到事务结束。它确实能给出可串行化，代价是写者互相等待、死锁要靠检测与回滚来处理，尾延迟极不稳定。

→ L8

可串行化快照隔离serializable snapshot isolation · SSI

乐观并发控制：事务在快照上自由执行，提交时检查「读过的数据是否已被别人改过」，冲突则回滚重试。它把等待换成了重试，所以在高冲突负载下会出现重试风暴，吞吐骤降。

别说「乐观锁一定比悲观锁快」。低冲突时它确实快；热点行高并发时，重试放大的代价会超过锁等待。

→ L8

MVCCmulti-version concurrency control

保留数据的多个版本，让读操作不需要阻塞写。它让「一致性快照」变得廉价，代价是旧版本必须有人回收（vacuum / GC），否则存储与扫描成本持续膨胀。

别忽略清理。长事务或长时间未提交的快照会让旧版本堆积，这是很多线上「磁盘突然涨满」的真因。

→ L8

幻读phantom read

同一事务内两次执行同一范围查询，结果集因为别人插入或删除而行数变化。它防不住是因为「要锁的对象还不存在」，只能靠范围锁或快照。

→ L8

丢失更新lost update

两个事务各自读到同一个旧值、各自算新值再写回，后写的那次覆盖了前一次的更新。典型修法：原子自增（UPDATE … SET x = x + 1）、显式加锁、或比较并交换（带版本号的条件更新）。

别说「读出来改完再写回」是安全写法。这是丢失更新的教科书形态，任何并发计数场景都会踩到。

→ L8

六 · 分布式系统的麻烦

这一组设在同一个前提下：在没有共享时钟、消息可能丢、节点可能只是「变慢」的世界里，我凭什么说这件事发生了？

故障fault

系统中的一个部件偏离其规格。它与失效（failure，系统整体停止提供服务）是两个层次：容错的设计目标是不让前者升级为后者。

别说「节点挂了」就完事。要说的是「它挂的方式是崩溃、是停止响应、还是变慢到超时」。三者的处理完全不同。

→ L9 分布式系统的麻烦

部分失效partial failure

分布式系统特有：一部分部件坏了，另一部分还在正常工作，而你无法从单点观测区分「对端坏了」与「网络慢到看不见」。这是全部分布式复杂度的源头。

→ L9

不可靠网络unreliable network

请求可能丢失、响应可能丢失、也可能只是延迟到超时之后才到。所以「没收到响应」永远不能推出「操作没发生」——这是所有重试与幂等设计的出发点。

别说「超时就当失败」。超时是未知，不是失败；把它当失败会导致重复执行副作用。

→ L9

超时timeout

等待响应的上限。它是分布式系统里唯一的故障检测手段，也是所有「假死/重复执行/脑裂」的来源——没有它系统会永远等下去，有它就必然误判。

别说「把超时调大点就好了」。调大只是把误判换成更长的用户等待，并让故障恢复更慢。

→ L9

无界延迟unbounded delay

网络延迟没有上界，只有分布。因此任何「超过 X 毫秒就算死」的判断在理论上都可能出错，工程上只能按概率与代价来选 X。

→ L9

时钟偏移clock skew

不同机器上的时钟走得不一样快，即使都用 NTP 同步也会有毫秒级偏差、还能被闰秒或虚拟机暂停放大。结论：不能用时间戳判断事件先后，要用逻辑时钟或版本号。

别说「用 created_at 排序就是顺序」。跨节点的时间戳排序会给出错误的因果顺序，且错得没有声响。

→ L9

单调时钟monotonic clock

只保证单调递增、不保证与真实时间对齐的计时器。测量耗时用它；表示「哪一刻」用墙上时钟。两者混用是分布式系统里的经典错误。

→ L9

真伪不确定unreliable failure detector

由于超时的存在，任何故障检测器都会犯两类错：误判存活节点为死（导致无谓切换），或迟迟发现不了真死（导致长时间不可用）。设计时只能选偏向哪一侧。

→ L9

拜占庭故障Byzantine fault

节点不仅会停摆，还会说谎，发出错误或伪造的消息。容忍它需要额外的签名与多数派机制，成本高得多，所以在受控的数据中心里通常不假设它，只在开放网络（区块链、航空电子）里假设。

别说「我们的系统要考虑拜占庭」。先问：你的节点是不是你自己部署、你自己运维的？如果是，故障模型通常是崩溃-恢复，不是拜占庭。

→ L9

七 · 一致性与共识

这一组专治「强一致」这四个字：你说「强一致」，具体承诺了什么、花了多少代价？面试里靠术语蒙混最容易过，也最容易在追问下翻车。

线性一致linearizability · linearizable consistency

整个系统看起来像只有一份数据，所有操作按某个全局顺序原子生效，且读到的值一定不早于最近一次已完成的写。它是单一对象的实时性保证。注意不要与可串行化混淆，后者是多对象事务的顺序保证。

别说「线性一致 = 强一致 = 可串行化」。线性一致管单对象的实时顺序，可串行化管多事务的等价串行，两者正交、可同时成立也可各自成立。

→ L10 一致性与共识

因果一致causal consistency

只保证有因果关系的操作顺序，无因果关系的并发写可以任意排序。它比线性一致弱，但它有一个重要性质：是客户端不需要协调就能得到的、最弱但不会让人觉得诡异的保证。

→ L10

最终一致eventual consistency

停止写入后，各副本最终会收敛到同一值。「最终」没有时间上界，所以这个说法本身几乎不构成可用承诺。写进文档时必须补上「收敛窗口多久、读到旧值的影响是什么」。

别说「我们最终一致所以没问题」。这是对不确定性的修辞掩盖：缺的是收敛时间的数量级。

→ L10

全序total order

任意两个事件都能比较先后。单主复制之所以简单，就是因为它把并发写放进了同一个全序里；无主与多主则只有偏序，冲突因此无处可藏。

→ L10

偏序partial order

只有部分事件可比（通常靠因果关系）。分布式系统的默认状态是偏序，要得到全序必须付协调代价，这就是共识算法存在的理由。

→ L10

因果causality · happens-before

若事件 A 的信息可能影响事件 B，则 A 因果先于 B。判断因果不需要真实时间，只需要消息传递的链。这是朗波特时钟与版本向量的基础。

→ L10

版本向量version vector

每个副本维护一个「见过的版本号」向量，比较两个向量就能判断是「A 包含 B」「B 包含 A」还是「并发」。它精确，但大小随副本数增长，所以通常只用于少量副本或按需压缩。

→ L10

共识consensus

让多个节点对某个值达成一致，且一旦达成不可反悔。它等价于「全序广播」与「原子提交」，是分布式系统里最强的协调原语，代价是每次决策至少一轮网络往返。

别说「用 Raft 就高可用了」。共识解决的是一致性，吞吐由往返延迟与批次决定；跨地域部署时它反而会放大写延迟。

→ L10

全序广播total order broadcast

所有节点以相同顺序收到相同消息。它与共识等价（可以互相实现），也是把「复制日志」变成「状态机复制」的那座桥。

→ L10

两阶段提交two-phase commit · 2PC

协调者先让所有参与者准备（投票），再统一提交或回滚。它保证原子性，但在协调者崩溃时会留下「参与者卡在已准备、既不能提交也不能回滚」的状态。这是它最著名的失败模式。

别说「2PC 保证一致性」。它保证的是原子提交，代价是可用性：协调者成了单点，且参与者在不确定期间必须一直持锁。

→ L10

栅栏令牌fencing token

每次获得锁时拿到一个单调递增的编号，下游资源拒绝编号更小的写入。它解决的是「持锁者以为自己还持锁，其实已被判定失效」。只有令牌能让被保护资源自己识别过期的持有者。

别说「加了分布式锁就安全了」。没有栅栏令牌的锁在 GC 停顿或网络抖动后仍然会双写。

→ L10

CAP 定理CAP theorem

网络分区发生时，一致性与可用性只能选一个。它对设计的真实意义不是「三选二」，而是「分区一定会发生，所以先决定分区期间拒服务还是给旧数据」。

别说「我们选了 AP 所以可用」。要说清：分区期间写会被接受但可能冲突、读可能读到旧值，以及冲突之后怎么收敛。

→ L10

八 · 批处理、流处理与衍生数据

这一组关心的是可重算性：这份结果是何时算的、重算一遍会得到同一个答案吗？

批处理batch processing

读取一批有界输入、跑完产出结果、然后退出。它的核心优势是可以重跑：同样的输入必然得到同样的输出，所以衍生数据可以由记录系统重建。

别说「批处理就是慢」。慢的原因是全量扫描与落盘，换来的是可重跑与可审计，这是它比流处理更适合做「权威衍生数据」的理由。

→ L11 批处理

流处理stream processing

对无界输入持续处理并输出。它把「什么时候算完」这个问题暴露出来：没有终点，所以只能用窗口、水位线这类约定来判断「这一刻的数据够了吗」。

→ L12 流处理

有界bounded

输入有明确终点（一个文件、一天的日志）。有界数据才能定义「处理完成」。

→ L11

无界unbounded

输入持续到达、永不结束。所有「完成后」的语义在无界数据上都必须重新定义为「某个窗口内」。

→ L12

水位线watermark

对「事件时间小于 T 的数据应该都到齐了」的声明。它是流处理里唯一能触发窗口计算的机制，本质是用迟到数据换及时性的一个旋钮：水位线放得保守，结果准但慢；放得激进，快但会漏。

别说「流处理是实时的所以没有延迟问题」。窗口结果的正确性完全取决于水位线策略，而这必须先问「业务能容忍多晚的数据被丢弃」。

→ L12 与 L13 流式系统的哲学

事件时间event time

事件实际发生的时间，由产生它的设备记录。它与处理时间（处理节点看到它的时间）可能相差任意长：离线补传、客户端时钟错、队列积压都会拉开两者。

→ L12

处理时间processing time

处理节点接收事件时的本地时钟。用它做窗口简单、不会等迟到数据，但重跑同一批数据会得到不同结果，这就破坏了可重跑性。

→ L12

幂等idempotent

执行一次与执行多次的效果相同。它是「至少一次」投递能变成「恰好一次」效果的唯一实用手段：不消除重复，而是让重复无害。

别说「我们用了恰好一次」。多数系统给的是「至少一次投递 + 幂等写」，说清这一点比宣称恰好一次可信得多。

→ L12

恰好一次exactly-once

端到端语义：效果上每个事件只被处理一次。实现方式是「去重（幂等写）+ 原子提交偏移量与输出」，缺一不可；跨系统的输出通常拿不到这个保证。

→ L12

反压backpressure

下游处理不过来时向上游施加压力（阻塞、限流、丢包）。没有反压的系统在过载时不会变慢，而是会崩掉或无限堆积——这是最常见的容量事故形态。

→ L12

流式连接stream join

把两条无界流按某个键或时间窗口拼在一起。难点全在「另一边还没到怎么办」：要么缓存一侧（状态无限增长），要么用窗口界定（结果不完备）。

→ L12

端到端原则end-to-end argument

一个功能只有在通信两端实现才算真正可靠；网络中间层的检查只能作为优化，不能作为保证。它对数据系统的直接推论：去重、校验、确认必须在最终消费者那里完成，消息队列的「可靠投递」承诺到不了应用语义。

→ L13 流式系统的哲学

及时性timeliness

用户观察到的状态有多接近真实状态。违反及时性意味着「数据是旧的」，这是可接受的，只要说清旧多久。

→ L13

完整性integrity

数据没有丢失或损坏。违反完整性意味着「数据永远不对了」，这不可接受，且不能用「最终一致」来辩护。

这是全书最该背下来的一句区分：违反及时性叫最终一致，违反完整性叫永远不一致。把两者混为一谈是评审里最贵的错误。

→ L13

数据流图dataflow

把系统看成「数据集 → 变换 → 数据集」的有向图，而不是「服务调用服务」。这种视角下，「这个报表的数字从哪来」可以逐跳回溯到记录系统，也是判断衍生数据能否重建的唯一办法。

→ L13

九 · 工程与伦理

这一组不是术语，是评审里必须能当场回答的问题。

预测分析predictive analytics

用历史数据训练模型去推断个体属性或行为。它的伦理风险不在于算法本身，而在于它把过去的偏见固化成对未来的判决，并且当事人无从申辩。

→ L14 做正确的事情

数据最小化data minimization

只收集当下有明确用途的数据。它是应对「以后可能有用」这种采集冲动的最有效原则：不收集的数据不会泄露、不会被滥用、也不会成为合规负债。

别说「先收集着，以后可能用得上」。这是数据系统里代价最高的一句话，因为它把风险敞口永久化了。

→ L14

被遗忘权right to be forgotten

用户要求删除个人数据时，删除必须传播到所有衍生数据（备份、索引、物化视图、日志、训练集）。这直接暴露了你对衍生数据的治理能力：删不掉，说明你不知道数据流到哪去了。

→ L14

隐私privacy

对「谁能观察、推断、影响一个人」的控制权。在数据系统里它不是「加密就行」，而是「谁能查、能查多久、能关联到什么粒度」。
