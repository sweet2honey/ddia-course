全书速查

面试前十分钟看的那张纸。六张对照表、一棵分片决策树、一份银弹失效边界、一套评审追问清单。每一格都对应书里的一处论证，标了章号，随时能回去核。

〇 · 一条主线

没有解决方案，只有权衡取舍 → 先问约束（数据量、延迟预算、故障模型、谁能等） → 再问选型（复制／分片／模型／存储引擎） → 然后必须说出放弃了哪条不变式 → 最后给出失效时的现象与监控指标。四步缺一步，这段设计就还不能进评审文档。

第 2 章给出的三个非功能维度，是后面所有取舍的坐标系：

  1. 可靠性（reliability）：出故障时还能正确工作。故障 ≠ 失效；容错是让故障不变成失效。
  2. 可伸缩性（scalability）：负载涨了还有合理办法应对。先量化负载，再谈「可扩展」。
  3. 可维护性（maintainability）：可运维、简单、可演化。这是唯一一项你每天都要付利息的。

一 · 一致性谱系（从弱到强）

「强一致」不是一个词，是一族词。评审里说错档位，等于没说。下表每行的「代价」列才是被追问时的答案。

保证承诺什么典型实现代价 / 失效现象
最终一致
eventual		停止写入后，副本终将收敛到同一值。异步复制、无主 + 提示移交「最终」没有上界；读到的旧值无法自证是旧的。ch6
读己之写
read-your-writes		用户总能看到自己刚提交的写入。写后读主库、按用户粘会话、记住自己的时间戳跨设备/跨账号失效；换设备就退回旧值。ch6
单调读
monotonic reads		看到某一时刻后，不会又看到更早的时刻。按用户哈希固定副本副本故障切换时会破；需要重新固定。ch6
一致前缀读
consistent prefix		因果相关的写入，按因果顺序被看到（问题在回答之前）。把有因果的写入放同一分片、用逻辑时钟排序跨分片就破；「因果」需要显式携带。ch6
因果一致
causal		所有节点按同一因果序观察事件；并发事件可不一致。版本向量、Lamport 时钟元数据随客户端增长；并发写仍要合并策略。ch6
线性一致
linearizable		表现得像只有一份副本，且每次读写瞬时原子生效。单主 + 同步复制、共识（Raft/Paxos）、单节点自增 ID响应时间至少与网络延迟抖动成正比（Attiya–Welch）；分区期间不可用。ch10

被问「你们是强一致吗」，正确答法不是「是/不是」，是报档位：

「我们的读是最终一致，延迟上界 p99 约 200ms；对账场景额外加一条读己之写，靠写后 1 秒内读主库实现；跨分片的转账依赖线性一致的租约服务发号，这里分区时会拒绝写入而不是返回旧值。」

三句话里出现了三个不同档位、一个数字、一个分区时的行为选择——这就是「能被追问」的样子。

可串行化的三种实现

  • 实际串行执行：单线程逐个跑，全内存 + 存储过程。吞吐上限 = 单核；适合分片后的事务。VoltDB、Redis 的路子。
  • 两阶段锁（2PL）：读写都加锁并持有到提交。能防一切，但写会阻塞读，死锁要检测；尾延迟最差。MySQL 8 前
  • 可串行化快照隔离（SSI）：乐观，提交时检查读写依赖，冲突则中止。不阻塞，但冲突率高时重试放大。PostgreSQL

四个最常被漏掉的异常

  • 丢失更新：读—改—写循环互相覆盖。修法：`SELECT FOR UPDATE`、原子自增、或让更新带上旧值做 CAS。
  • 写偏斜：两个事务各读一部分、各写另一部分，前提都成立但结论互斥（双医生同时请假）。修法：显式加锁或可串行化。
  • 读偏斜：同一次事务里两次读看到不同快照（转账前后看到中间态）。修法：快照隔离。
  • 幻读：查询条件的结果集被别人插入改变。修法：索引范围锁。

三 · 复制方案对照

方案写入落在哪读从哪来冲突 / 收敛什么时候选
单主
leader-based		唯一领导者任意副本（可能陈旧）无冲突；切换时可能丢最近写入默认选项。写入不跨地域、能接受切换暂停。
多主
multi-leader		任一领导者本地领导者（低延迟）必须解冲突：LWW / 版本向量 / CRDT / 人工多地域写入、离线优先（local-first）、协作编辑。
无主
leaderless		客户端并发写 w 个并发读 r 个 + 读修复版本向量检测并发；提示移交补漏要高可用、能容忍弱一致。Cassandra / DynamoDB / Riak。

仲裁（quorum）的三条硬事实：

① w + r > n 才保证读写集合相交；取多数（> n/2）能同时容忍 ⌊n/2⌋ 个节点失效。

② w + r > n 不等于线性一致：节点从旧副本恢复、再平衡期间节点对 n 的组成看法不一、写部分成功不回滚、时钟快的节点静默丢写——任意一条都能打破它。

③ 调小 w/r 换的是延迟和可用性，不是「更好的性能」，代价是更容易读到陈旧值。

四 · 分片决策树

① 真的需要分片吗？
单机能扛住数据量与写入吞吐？扛得住就别分——分片是重量级方案，只有大规模才值得。读吞吐不够先用读副本，不是分片。

② 分区键选谁？
选那个「几乎每个查询都带着它」的字段。键选错：跨分片查询 + 未来难改。

③ 范围还是哈希？
范围分片：扫描友好、热点风险高（时间戳/自增 ID 天然热点）。哈希分片：均匀、丢范围扫描。折中：复合键（前缀哈希 + 后缀排序）。

④ 热点怎么办？
加随机后缀拆键、应用层缓存、或把热键单独拎出来。倾斜（skew）是分布问题，不是负载问题。

⑤ 再平衡谁来定？
全自动方便但会和自动失效检测叠加成级联失效（过载→误判死→迁数据→更过载）。有人工确认这一步的折中通常最稳。

⑥ 二级索引怎么切？
本地索引（按文档分区）：写只碰一个分片，读要扇出所有分片 + 尾部延迟放大。全局索引（按词项分区）：读单分片，写要跨分片原子更新。二选一，没有免费的。

五 · 批与流

批处理

  • 定义性质：有界输入、可重跑、幂等。错了重跑一遍就对了——这是它最大的运维红利。
  • 代价：延迟以小时/天计；输出是快照，不是状态。
  • 关键机制：分布式文件系统（数据本地性）、shuffle（排序落盘）、数据流引擎（DAG 而非 Map→Reduce 两步）。
  • 用在：ETL、训练集、全量重建索引、对外提供衍生数据。

流处理

  • 定义性质：无界输入、持续运行；正确性靠「可重放 + 幂等 + 去重」，不是靠事务。
  • 代价：状态要持久化，迟到数据要处理，顺序要自己扛。
  • 关键机制：日志式代理（保留 + 重放）、CDC、事件时间窗口 + 水位线、恰好一次 = 至少一次投递 + 幂等去重。
  • 用在：派生视图、缓存失效、跨系统同步、实时指标。

「恰好一次（exactly-once）」到底保证了什么：保证的是效果恰好一次，不是投递恰好一次。实现方式必定是「至少一次投递 + 接收端幂等 / 去重表 / 事务性写偏移」三者之一。所以它只在端到端范围内成立——中间任何一个环节把消息重放了却不去重，这个保证就没了。ch12 / ch13

六 · 银弹失效边界

方案它解决什么在哪失效
事务把并发与部分故障收成一次中止跨异构存储的 2PC 对协调者故障极敏感；弱隔离下写偏斜照旧。
2PC多节点原子提交协调者崩溃后参与者持锁等待；启发式决策破坏原子性。
CRDT并发写自动收敛，无需协调只对特定数据类型成立；元数据随副本数增长；语义上「合并」未必符合业务。
幂等消费者重试安全需要稳定的去重键；去重表本身会无限增长，要窗口化。
CDC把数据库变更变成流模式演化会让下游解析失败；顺序依赖单分区；快照 + 增量切换点容易漏。
共识（Raft/Paxos）线性一致的复制状态机每次写入至少一次往返多数派；跨地域部署延迟直接翻倍；只保护经由它的状态。
分布式锁 / 租约互斥进程暂停（GC、换页）会让持锁者「假活」；必须配栅栏令牌（fencing token）。

八 · 常见误用

  • 「CAP 三选二」。错。分区不是选项，是必然发生；正确说法是「分区期间要么一致要么可用」。CAP 已被更精确的结果取代，如今只剩历史意义。ch10
  • 「用了 ACID 数据库就没有并发问题」。错。多数「ACID」数据库默认是读已提交或快照隔离，写偏斜照旧发生。ch8
  • 「最终一致 = 弱，无所谓」。错。最终一致必须能量化「最终」有多远，否则不可运维。ch6
  • 「复制延迟是运维问题」。错。它是应用要显式处理的一致性模型问题。
  • 「分片能提升查询吞吐」。不一定。扇出到所有分片的查询，加节点只会让尾延迟更糟。ch7
  • 「批处理过时了，都上流」。错。批处理的「可重跑」是别的方案换不来的，很多流系统靠批补历史。ch13
  • 「事务慢，所以不用事务」。先看慢在哪：是锁、是 2PC 往返、还是磁盘 fsync。三者代价差一个量级。ch8
  • 「时钟大致准就够了」。错。跨节点排序、租约、LWW 冲突解决都建立在时钟上，一次 NTP 跳变就能让顺序反转。ch9

九 · 一句话带走

每次评审只做一件事：把「我们用了 X」改写成「在约束 C 下，我们选了 X，放弃了不变式 I，失效时表现为 P，监控指标是 M」。五个空填不满，这个决策就还没想清楚。
